先调用 `skill` 工具加载 `doc-flow`，并严格按技能契约输出。
用户参数：$ARGUMENTS

规则：
- 如果参数里包含/看起来像文件路径（.md/.txt/.docx/.pptx/.xlsx/.pdf），先用 `doc.import` 导入后再判断。
- 领域判断优先根据仓库信号；本仓库为软件工程领域时直接进入该域。
- 输出文档清单时允许多选，优先推荐仓库已有模板/文档类型。
- 不要擅自定“必须产出”的文档；用“建议/可选”并让用户确认。
- `doc.template.render` 是工具，不是 skill，禁止调用不存在的 skill（例如 `doc-template-render`）。
- 可用模板 templateId 仅限：
  tech.prd, tech.tdd, tech.sdd, eng.requirements_analysis, eng.feasibility_study,
  qa.test_plan, ops.runbook, ops.postmortem, security.threat_model,
  eng.release_notes, mgmt.meeting_minutes, mgmt.weekly_report, legal.contract_review_notes.
- `doc-style` 是 skill，必须在填充正文后调用以整理样式与元信息。

流程（必须按顺序执行）：
1) 输出 `doc.flow.v1` 的 YAML（包含领域 + 文档清单 + 推荐项 + 缺失信息）。
2) 询问用户选择需要的 doc_type（支持多选）。如果用户已明确文档类型，直接进入下一步。
3) 对每个 doc_type 生成骨架：
   - 有模板则用 `doc.template.render`
   - 无模板则用 `doc-outline`
4) 汇总所有骨架，请用户确认/补充缺失信息。
5) 用户确认后，对每个 doc_type 调用 `doc-fill` 生成正文。
6) 询问并收集样式与元信息（字体/字号/行距/目录层级/作者/版本/日期/状态/是否提供 reference docx）。如用户未提供，直接使用默认样式并说明默认值。
7) 先调用 `skill` 工具加载 `doc-style`，再统一整理（元信息 + 标题层级 + 目录 + 排版），输出 styled_markdown。
8) 汇总 styled_markdown 并执行 `doc-review`，给出阻塞项/缺失项。
9) 用户确认后，若需要导出 Word：将最终 Markdown 写入文件，再用 `doc.convert` 转成 .docx（附带 toc 与 reference docx）。
10) 如涉及对外发布/分享，导出前先运行 `doc.redact`。

输出要求：每个阶段都清晰标注（Phase A/B/C...），多文档输出需按 doc_type 分组。
